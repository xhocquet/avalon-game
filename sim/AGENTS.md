# Shared Simulation Scope

- `sim/` is authoritative deterministic gameplay compiled by both `client/` and `server/`. Keep client/server behavior aligned when editing here.
- Data assets live at `client/Sim/Data/` because Godot `res://` requires them inside the Godot project. The server copies those `.bytes` files at build/runtime.
- Both sides call `SimulationSetup.RegisterSystems(...)` and `SimulationSetup.InitializeWorld(...)` through their `ISimulationCallbacks` implementations.
- Godot client callbacks poll local input and send commands; server callbacks do not poll local input because Klotho injects client commands into the authoritative server simulation.

# Heroes

- A hero's numbers come from [`HeroAsset`](Assets/HeroAsset.cs) (rows in the `AssetIds.Hero*` block), reached via `FactionAsset.HeroAssetId`. `PlayerStatsAsset` is gone: its hero stats moved here and its gold fields to `MatchRulesAsset`.
- **Distances are metres, and the scale is 100 game units to 1 metre.** The published stat blocks these rows are authored from use game units (a 350 move speed, a 175 attack range), so divide by 100 on the way in. Health, mana, damage, and the resists are unitless; regen is per 5 seconds, the unit it is authored and displayed in.
- An asset row is only the **spawn seed**. Live values that skills and items change belong on a component, and changes route through `Stats.Add(StatType, delta)` rather than writing fields. Never read a live value back off the asset.
  - Every growing stat is a `Base*` + `*PerLevel` pair. `StatsComponent.From` seeds the `Base*` half; `ExperienceSystem` adds the growth. The flat stats (`MoveSpeed`, `AttackRange`, `AcquisitionRange`, crit, the radii) have no pair.
  - `MoveSpeed` → `Stats.MoveSpeed`; `NavigationAgentSystem` pushes it onto the nav agent every tick, `CommandSystem`'s direct-move path reads it.
  - `BaseAttackDamage` → `Stats.AttackDamage`; `AttackRange` → `Stats.AttackRange`; `BaseHealth` → `Stats.MaxHealth` (`Health` holds only the current HP, which is transient state rather than a buffable stat).
  - `BaseArmor`/`BaseMagicResist` → `Stats.Armor`/`Stats.MagicResist`. `DamageApplication.Mitigate` picks one on the hit's `DamageType` and scales by `100 / (100 + resist)`, so stacking approaches but never reaches immunity. A **negative** resist takes the mirrored branch (`2 - 100 / (100 - resist)`), amplifying toward 2x rather than passing the hit through raw.
  - `AcquisitionRange` is absolute, not a multiplier on attack range — `TargetAcquisitionSystem` reads it straight off `Stats`. Turrets author it equal to their `AttackRange` because they cannot chase.
  - `BaseAttackSpeed` is **attacks per second**, scaled by `Stats.BonusAttackSpeed` and capped by `StatsComponent.AttacksPerSecond`. Nothing stores a tick period: [`CombatTiming.CooldownTicks`](CombatTiming.cs) derives it at the moment of the hit, so bonuses stay additive on the rate, rounding never compounds, and the authored number keeps its meaning if the tick rate changes. The view shares that helper rather than deriving its own.
  - `PathingRadius` feeds the nav agent; `GameplayRadius` → `Stats.GameplayRadius` is what a hit tests against — the reach and projectile checks measure to it, never to the thinner `PathingRadius`; `SelectionRadius` is view-only and neither the sim nor the view reads it yet. `AttackWindup`, `AttackSpeedRatio`, mana and the regens are authored but not yet wired to anything.
  - `CritChance`/`CritDamage` → `Stats.CritChance`/`Stats.CritDamage`, rolled by [`CriticalStrikes`](CriticalStrikes.cs). **Crit is opt-in per damage source**: `DamageSystem` passes `canCrit: true` for auto-attacks, skill damage does not, so a projectile never crits by accident. The multiplier lands *before* mitigation, so a crit is worth the same fraction against any armor value, and `AttackHitEvent.IsCrit` carries the verdict to the view. Every hero row authors `CritChance: 0` today — the mechanic is live, the data is not, so nothing crits until an item or buff adds some through `Stats.Add`.
  - **`AttackRange` is edge-to-edge.** [`CombatRange.ReachSq`](CombatRange.cs) is the one place that turns it into a centre distance, adding both bodies' `GameplayRadius`. Measuring centre-to-centre instead leaves every melee hero unable to touch a turret: structures stand in a hole in the navmesh ~1.6m across, wider than a 1.25m reach.
- The spawned entity stores `Hero.HeroAssetId`, so any system can get back to the row without going through the faction.
- Hero-specific *code* lives in an [`IHeroBehavior`](Heroes/IHeroBehavior.cs) selected by `HeroAsset.BehaviorId` through [`HeroBehaviors.Get`](Heroes/IHeroBehavior.cs), which lazily builds only the behaviors a match actually asks for. `HeroFactory` calls `OnSpawn`; [`HeroBehaviorSystem`](Systems/HeroBehaviorSystem.cs) calls `OnTick` for every hero each tick.
- Behaviors are **stateless singletons**. Components are the only rollback-safe storage — a field on a behavior survives a rollback and desyncs the client. Add a component in `OnSpawn` and mutate it in `OnTick`.
- Components can't be subclassed (they are `[StructLayout(Sequential)]` structs snapshot by value), and adding a hero must never change the component layout heroes share.
- Adding a hero: allocate ids in `AssetIds`, drop a `client/Sim/Data/Assets/heroes/<hero>.json` holding its `FactionAsset`, `HeroAsset` and four `SkillAsset` rows, regenerate `Assets.bytes`. Code is only needed when it wants behavior no existing `BehaviorId` covers.

# XP & Leveling

- Progression lives on [`ExperienceComponent`](Components/Behaviors/ExperienceComponent.cs) (Level, lifetime Experience), added to every hero by `HeroFactory`. It is deliberately not on `StatsComponent` — Stats holds buffable combat values that skills and items write through `Stats.Add`; XP is the input that *produces* those writes.
- [`XpRulesAsset`](Assets/XpRulesAsset.cs) (row `AssetId: 115`) holds per-victim-type kill rates, the level curve, and the shape of the growth curve. Rates are flat across players; a kill is worth what the victim is worth. **Per-level stat gains are not here** — they are per-hero, on `HeroAsset`, so two heroes can scale differently off the same curve.
- [`StatGrowth`](StatGrowth.cs) is that curve: `value(level) = base + growth * n * (A + B * n)` with `n = level - 1`. The ramp back-loads the gain, so a late level is worth more than an early one, and `StatGrowthCurveA`/`StatGrowthCurveB` are authored so the ramp hits exactly 1 at the cap — which puts a capped hero on `Base + PerLevel * (MaxLevel - 1)` and is what lets a row be authored straight off a published min-max range. `StatGrowthTests` fails if that pair drifts.
- The curve is an arithmetic series in integers — level 2 costs `XpToSecondLevel`, each level after costs `XpPerLevelIncrement` more. `XpRulesAsset.TotalXpForLevel(level)` is the closed form and is what UI should use for a progress bar.
- **Awarding** happens at the kill site through [`ExperienceRewards.AwardForKill`](ExperienceRewards.cs), called from `DeathSystem` (everything on the board) and `RespawnSystem.BeginRespawn` (heroes, which never reach `DeathSystem`). Credit goes to **whoever landed the fatal hit** (`Health.LastDamagerUnitId`, recorded by `DamageSystem`) and nowhere else — no team split, no proximity share. Only heroes carry an `ExperienceComponent`, so a kill credited to a minion or turret pays out nothing. Friendly fire and unattributed deaths award nothing.
- `DeathSystem` resolves the killer once per corpse into `DeadUnitSnapshot` (entity + its `UnitIdComponent` + team/owner) and pays every award out in a pass **before** the destroy pass, so a killer that dies on the same tick still earns what it killed. `UnitDiedEvent` carries `DestroyerUnitId`/`DestroyerUnitTypeId` for the view.
- **Spending** happens in [`ExperienceSystem`](Systems/ExperienceSystem.cs), registered right after `DeathSystem` so a kill lands its level on the same tick. It is the only writer of `Level`, walks every `StatType` and adds `StatGrowth.Between(oldLevel, newLevel)` of the hero's own growth via `Stats.Add`, grows the HP pool through `HealthApplication.GrantMaxHealth` (which tops current HP up by the same delta, skipping a hero at 0 HP awaiting respawn), and raises one `HeroLeveledUpEvent` carrying the level reached even when several levels land at once.
- It adds the **difference between the two levels**, not a per-level step repeated — the curve is not linear, so a multi-level tick would otherwise land somewhere else entirely. The base cancels out of that difference, which is why no base/bonus split is needed and item bonuses simply stack on top.
- XP is lifetime-earned and never reset, so it survives death and respawn for free — the hero entity is never destroyed.

# Gold

- The wallet is [`InventoryComponent`](Components/Behaviors/InventoryComponent.cs). Gold arrives two ways: a passive trickle and kill bounties. Both are integers; there is no fractional gold.
- **Pacing** is on `MatchRulesAsset` (row `AssetId: 110`), beside the match clock it is measured against: `StartingGold` is what `HeroFactory` seeds the wallet with, `GoldStartDelayMs` gates when the trickle opens, `GoldTickIntervalMs`/`StartingGoldPerTick` are its rate. [`InventorySystem`](Systems/InventorySystem.cs) gates on `frame.Tick`, not on how long a hero has existed, so a hero spawning late out of faction select doesn't get its own private delay. `GoldAccrualRemainderMs` doesn't bank during the delay, so the first payout lands one full interval after the gate opens.
- **Bounties** are on [`GoldRulesAsset`](Assets/GoldRulesAsset.cs) (row `AssetId: 118`), the gold twin of `XpRulesAsset` — per-victim-type, flat across players. [`GoldRewards.AwardForKill`](GoldRewards.cs) mirrors `ExperienceRewards` exactly: same two call sites (`DeathSystem`, `RespawnSystem.BeginRespawn`), same `MatchStats.IsCreditableKill` gate, credit to the fatal hit only. Only heroes carry an `InventoryComponent`, so a kill credited to a minion or turret pays nothing.
- `GoldPerAssist` is authored but unread — assists need a damage-participation window that `Health.LastDamagerUnitId` cannot provide. See the TODO in the root README.
- Gold survives death and respawn for the same reason XP does: the hero entity is never destroyed. `StartingGold` is seeded once at spawn, not re-granted on respawn.

# Stats

- [`StatsComponent`](Components/Behaviors/StatsComponent.cs) is one `FP64` per [`StatType`](Enums.cs), stored as a `fixed long` buffer of raw 32.32 values rather than named fields. That is deliberate: a stat cannot be forgotten in a `switch`, every write goes through the same clamp, and a fractional or percentage modifier (`+0.5` attack damage, `+2.9%` attack speed) survives instead of truncating. Named `readonly` properties keep call sites reading as `stats.MoveSpeed`.
- `StatType` **indexes that buffer**, so its values must stay contiguous from 0 and [`StatRanges.Rows`](StatRanges.cs) must carry one row per entry in the same order. Nothing serializes the enum, so renumbering it is safe.
- [`StatRanges`](StatRanges.cs) is a `(Min, Max, Initial)` row per stat and lives in **code, not the asset JSON** — these are the bounds that stop the sim dividing by zero, inverting a mitigation curve, or leaving a unit with no health pool, the same class of thing as `CommandLimits`. Tuning belongs in the asset row, inside them.
- A default-constructed block is all zeroes, which is out of range for anything with a non-zero floor (a `BaseAttackSpeed` of 0 would divide by zero in the cooldown). **`StatsComponent.Create()` is the only correct starting point**; `From(IUnitStatsAsset)` builds on it, and every factory goes through one of the two.
- Damage is `FP64` end to end — `Health.Current`, `DamageApplication`, `SkillAsset.Damage`, `Projectile.Damage`, `ShopItemAsset.AttackBonus`, `AttackHitEvent.Damage`, `Player.DamageDealt`. Rounding happens only at the edges: `MatchResult` for the scoreboard JSON, and `.ToFloat()` in the view.
- Gold accrual is **not** a stat. `GoldPerTick` sits on `InventoryComponent` beside the wallet it feeds.

# Skills & Upgrades

- Every hero has four skill slots — `Primary`, `Secondary`, `Tertiary`, `Ultimate` ([`SkillSlot`](Enums.cs)) — each ranked 0-4. The slot indices are the indices into `SkillsComponent`'s fixed buffers and into `HeroAsset.Skill1..4AssetId`, so they must stay 0-based and contiguous.
- Numbers live in [`SkillAsset`](Assets/SkillAsset.cs), four rows per hero in the `AssetIds.Skill*` block (500-519). Every hero owns its own rows even where they currently match, so retuning one hero's skill never touches another's. `CooldownMs` is authored in milliseconds; `SkillActions.CooldownTicks` converts it once, at cast time, with the same ceiling-divide `RespawnSystem` uses. The row is one flat shape for every skill — `Damage`/`DamagePerRank` (resolve with `DamageAtRank`), the `Projectile*` block, and the `Min`/`MaxCastRange` band — and fields a given skill doesn't use sit at 0. **A skill's whole tuning surface is its one row**: nothing about damage, speed, range, radius, count, spacing, or muzzle offset may be decided in code. `CrystalBulletsTests.EveryProjectileNumber_TracesBackToTheAssetRow` fails if any of it drifts back into a literal.
- State lives on [`SkillsComponent`](Components/Behaviors/SkillsComponent.cs): unspent points, the four `SkillAsset` ids, ranks, and cooldowns, all as `fixed int` buffers (52B). `HeroFactory` copies the ids off `HeroAsset` at spawn, so nothing downstream reaches the asset registry to find out which skills a hero owns.
- **Earning**: a hero spawns with 1 point (level 1 counts as a level) and `ExperienceSystem` grants one per level gained, so points always equal level. Points are not a stat and do not route through `Stats.Add` — the tree spends them itself.
- **Spending and casting** both go through [`SkillActions`](Heroes/SkillActions.cs), dispatched from `CommandSystem` by `UpgradeSkillCommand` / `CastSkillCommand`. `CommandValidation` range-checks the slot first, and it is the only thing standing between a wire value and an unchecked fixed-buffer index. A cast starts its cooldown *before* running the effect, so an effect that kills or respawns its own caster cannot leave the slot free.
- **Targeting**: `CastSkillCommand` carries a planar `TargetX`/`TargetZ` aim point, the same envelope-checked pair `MoveCommand` uses. `SkillActions` flattens it and hands the effect a [`SkillCastContext`](Heroes/IHeroSkillSet.cs) — caster, player, slot, asset, rank, caster position, target position. Add to that struct rather than to `OnCast`'s parameter list. Self-cast skills ignore the target; a skillshot reads it as a direction. The client aims from `CameraController.ScreenToGround` and deliberately does *not* snap it to the navmesh the way a move order does.
- **Cast range** is the `MinCastRange`/`MaxCastRange` pair on the row, applied by [`SkillAim.ClampToCastRange`](Heroes/SkillAim.cs) before any effect sees the aim point. Both ends are optional — omitted in JSON (0) means unbounded there, which is what every skill had before the band existed. An out-of-band aim is **clamped along the line the client aimed, not rejected**: a modified client casting across the map lands at its own edge, and a legitimate over-aim still fires where the player pointed. `CommandValidation` keeps only the world-envelope check, because the band is a game-state rule and belongs beside the cooldown and rank checks. `SkillAim.Direction` is the shared aim-direction helper, with the caster's `Rotation` as the fallback when the aim point sits on the caster.
- Skill cooldowns are burned down by [`TimedEffectSystem`](Systems/TimedEffectSystem.cs), the one pass that owns every per-tick countdown in the frame — attack cooldowns, skill cooldowns, buff expiry, attack procs. It is registered before `HeroBehaviorSystem` so skill state is current when behaviors tick, and ahead of `DamageSystem` so a cooldown that reaches 0 is spendable on the same tick. A cast on tick N loses one tick to it on that same tick, because commands are delivered before the Update phase — identical on both peers, so it is not an off-by-one. **A new countdown belongs in that pass, not in a system of its own.**
- Hero-specific skill *code* lives in an [`IHeroSkillSet`](Heroes/IHeroSkillSet.cs) selected by `HeroAsset.SkillSetId` through [`HeroSkillSets.Get`](Heroes/IHeroSkillSet.cs), which lazily builds only the sets a match actually asks for — one folder per hero under `Heroes/` (e.g. `Heroes/Shroom/ShroomSkills.cs`), each set owning all four of that hero's slots, while the shared plumbing sits at the root of `Heroes/`. Everything under `Heroes/` is namespace `...Sim.Heroes`; the per-hero folder holds what that hero owns, it is not a namespace boundary. This is deliberately separate from `BehaviorId`: that selects spawn/tick logic and is 0 for every hero, while skills are per-hero from the start. Like behaviors, skill sets are **stateless singletons**.
- Most of the 20 skills are named but empty: each hero's set has one `Cast<SkillName>` per slot (e.g. `CastSpikyPunch`) with no body yet, so implementing one means filling in a single method. `OnRankGained` is likewise an empty per-hero hook, kept for rank effects like refreshing a cooldown.
- **Projectiles** are the one lifecycle built so far, and Crystal Giant's `CastCrystalBullets` is the worked example. A skill fires through [`SkillProjectiles.SpawnVolley`](Heroes/SkillProjectiles.cs) — Hairy Wizard's `CastHairball` is the same call with a `ProjectileCount` of 1, a wider `ProjectileRadius`, and a cast band — which creates one entity per bullet carrying a [`Projectile`](Components/Units/Projectile.cs); [`ProjectileSystem`](Systems/ProjectileSystem.cs) advances and resolves them, registered ahead of `DamageSystem` so a projectile kill reaches `DeathSystem` on the same tick. A projectile deliberately carries no `TeamComponent`/`Health`/`UnitIdComponent` — those are what would make it an attack target — so the firing team rides on the component as a plain int.
- Hit detection is proximity, not physics: `ProjectileSystem` rebuilds the same `SpatialHashGrid` broad phase `TargetAcquisitionSystem` uses, then narrow-phases the tick's swept segment against each candidate's `Stats.GameplayRadius`, resolving the nearest along the segment with `UnitId` as the tie-break. `CombatTargeting.IsSkillHittable` keeps structures out of skill hits by default.
- Damage from any source goes through [`DamageApplication.ApplyDamage`](DamageApplication.cs) — mitigation, the zero floor, `Health.LastDamagerUnitId`, and `AttackHitEvent` in one place, so a skill kill pays XP the same way an auto-attack does.
- Health going the other way goes through [`HealthApplication`](HealthApplication.cs), the mirror of that choke point: `ApplyHeal` clamps to `Stats.MaxHealth` and refuses to revive a unit at 0, `RestoreToFull` is the respawn path that deliberately skips that check, and `GrantMaxHealth` moves the pool and current HP together. Nothing else writes `Health.Current` upward.
- Events are one per phase: `SkillCastEvent` (Synced) for the cast, `SkillProjectileSpawnedEvent`/`SkillProjectileDespawnedEvent` (Regular, matched on `ProjectileId`) for each bullet, and `AttackHitEvent` for the damage. Every id born raises exactly one despawn.
- **Timed buffs** are the second lifecycle, and Crystal Giant's `CastHarden` is the worked example. A skill raises a stat through [`StatBuffApplication`](StatBuffApplication.cs) — the buff twin of `DamageApplication`, the one place the `StatsComponent` write and the [`StatBuffsComponent`](Components/Behaviors/StatBuffsComponent.cs) entry that owes it back happen together — and [`TimedEffectSystem`](Systems/TimedEffectSystem.cs) takes it off when its tick arrives, registered ahead of every reader of `Stats` for the frame.
  - Duration is stored as the **absolute expiry tick**, not a countdown, so expiry is one comparison per entry per tick and a rollback replay lands on the tick it did the first time. A buff applied on tick N for D ticks is worth its bonus on ticks N..N+D-1.
  - An entry records **what the stat actually moved by**, not the percentage asked for. `StatRanges` clamps inside `Set`, and the stat underneath moves on its own (a level-up, an item), so a revert that recomputed the fraction would hand back an amount that was never granted.
  - Entries are keyed by `(source asset id, stat)`, so a recast **refreshes** its own buff — the running copy comes off before the new one lands, which is also what stops a percentage compounding on itself. A different source stacks normally, up to `StatBuffsComponent.MaxEntries`.
  - `RespawnSystem.ClearActiveState` drops every buff on death rather than letting the clocks run out on a corpse.
  - Tuning is the row as usual: `BuffDurationMs` and the `BuffPercent`/`BuffPercentPerRank` pair, resolved with `BuffPercentAtRank`. Which stats a buff lands on is the skill's own business — Harden takes both `Armor` and `MagicResist`, one entry each.
- **Empowered attacks** are the third, and Crystal Giant's `CastSpikyPunch` is the worked example: a cast that does nothing on its own, arms [`AttackProcComponent`](Components/Behaviors/AttackProcComponent.cs) through [`AttackProcs`](AttackProcs.cs), and is spent by the next auto-attack that lands. It expires on a tick in the same `TimedEffectSystem` pass the buffs do, and dies with the hero the same way.
  - **`DamageSystem` is the only consumer**, so a skill or a projectile can never eat the charge the player is holding for an attack. It spends the proc at the point the attack is committed to — past the dead/friendly target checks — so a charge is never burned on a swing that does not happen.
  - The multiplier lands on the raw attack damage **before mitigation**, the same place `CriticalStrikes` puts its own, so the hit is worth 4x a plain hit against any armor value rather than 4x a mitigated number. Crit and proc stack multiplicatively.
  - One slot, not a buffer: a second arming **replaces** the charge waiting rather than queueing behind it, which is what re-arming should do and keeps the consume path one branch.
  - **An effect that modifies a hit describes itself in its own event, never as a flag on `AttackHitEvent`.** `AttackHitEvent.AttackHitId` (off the `AttackHitIdCounter` singleton) is the handle every event about that hit carries, and `AttackProcConsumedEvent` names its skill, its multiplier, and the hit it rode in on. One attack that spends several effects raises one event each; a flag or a single id field on the hit could only report one of them. `Damage` still carries the combined result, the way it does for a crit.
  - `DamageApplication.NextHitId` is public for exactly one reason: an effect that modifies damage on the way *in* has to raise its event before the hit exists, so `DamageSystem` takes the id first and hands it to both. Ids are allocated **whether or not anything is listening** — the counter is frame state, so a peer with no `EventRaiser` has to burn the same ids or the frames stop hashing the same.
  - `ProcResetsAttackCooldown` clears the caster's swing timer at **arm** time, so a punch cast right after an auto-attack goes out on the cast tick instead of waiting out the rest of that auto. Casts run before the Update phase, so the 0 is already there when `DamageSystem` reaches the attacker. The cooldown restarts from the empowered hit, so it buys one swing rather than a faster attack rate.
  - Tuning is the row: `ProcDurationMs`, the `ProcDamageMultiplier`/`ProcDamageMultiplierPerRank` pair resolved with `ProcDamageMultiplierAtRank`, and the reset flag. The multiplier is a **total**, not a bonus: 4 is 400% of a normal hit.
- **Heals** are the fourth lifecycle, and Pickle Knight's `CastRefresh` is the worked example: `HealPercent`/`HealPercentPerRank` (resolved with `HealPercentAtRank`) are a fraction of the target's **`Stats.MaxHealth`**, not a flat number, so a heal keeps its meaning as the pool grows with level. It goes through [`HealthApplication.ApplyHeal`](HealthApplication.cs) like every other upward write, which clamps the overheal and refuses a hero at 0 — a heal is never a resurrect, and `EvaluateCast` has already refused a dead caster before the effect runs anyway. Nothing raises an event for it yet, so the view has no heal number to draw.
  - Refresh is also meant to **cleanse**, and that half is deliberately unwritten: nothing in the sim applies a negative status yet. The TODO on `CastRefresh` is where it lands.
- **`SelfCast`** (0/1 on the row) is a skill with no aim. `SkillActions.TryCast` replaces the aim point with the caster's own position rather than clamping it, so the cast, its `SkillCastEvent`, and any telegraph all resolve on the hero whatever a modified client sent. The client reads the same flag through `SkillAsset.IsSelfCast`: `InputCapture.BeginSkillAim` fires the cast on key-*down* instead of entering the hold-to-aim path, because holding a key can only delay a cast whose target is already known.
- Not built yet: cast time, resource costs, respec, and rank prerequisites. A level gate would be a `MinHeroLevel` field on `SkillAsset` plus one rung in `SkillActions.TryUpgrade`.

# Match End & Results

- **The outcome is a team, not a player.** [`MatchOutcome`](Components/State/MatchOutcome.cs) (singleton, `EndTick`/`WinnerTeamId`/`Reason`) is the sim's record and the only thing anything downstream should read the winner from. Klotho's own `MatchEndStateComponent` carries `Ended` + a single `WinnerPlayerId` and cannot hold a reason, so `ScoreSystem` mirrors a *representative* player of the winning team into it purely to satisfy the engine. A win whose team has no hero left on the board reports `-1` there and is still a win in `MatchOutcome`.
- `MatchEndReason` is **recorded at the point the match ends**, never inferred. `MatchResultReader` reads it off the component; deriving it from `winner == -1` is what made every unresolvable crystal win read as a timeout.
- The **win condition keys off crystals, not heroes**: a team is in the match while its base stands, whether or not anyone is alive to defend it. `TeamPruneSystem` writes `MatchSetupState.ContenderTeamCount` once the teamless prune settles, and `ScoreSystem` only judges a match with 2+ contenders — otherwise a one-base map would insta-win on tick 0.
- [`GameOverEvent`](Events/GameOverEvent.cs) carries `WinnerPlayerId`/`WinnerTeamId`/`Reason` as `[KlothoOrder]` fields. Without them the generated `GetContentHash()` is just the type id, so a crystal win and a timeout hash identically and Synced-event divergence can't tell them apart. `IMatchEndEvent.Reason` maps to a literal telemetry string, not the enum name.
- **Per-player stats** live on [`Player`](Components/Units/Player.cs) (score, hero/minion/structure kills, deaths, damage) and are written only through [`MatchStats`](MatchStats.cs), the scoreboard's counterpart to `ExperienceRewards`. Both share `MatchStats.IsCreditableKill`, so kill credit and XP can never disagree about who earned what. `DamageApplication` credits damage, `DeathSystem` and `RespawnSystem` credit kills and deaths. Score values per victim type are `MatchRulesAsset` fields.
- [`MatchResult`](MatchResult.cs) is the read-out: outcome, duration, a `MatchContext` of the setup the round was played under, and one `PlayerResult` row per hero, sorted by (team, player) so the JSON and the scoreboard don't shuffle. The server's `MatchResultSaveSystem` writes it; the client's `ViewCallbacks` reads it off the verified frame when `GameOverEvent` confirms.
- **Resource tallies are keyed, not slotted.** `MatchContext.ResourceTypes` is the kinds the round actually used — every kind an oasis ejects, plus any kind a player is holding, so hand-placed pickups don't leave an unlabelled tally. Each `PlayerResult.Resources` carries one `ResourceTally` per entry in that list, same order, so nothing has to know `PickupTypes` slot numbering to read the file.
- **`PlayerResult.Name` is the one field the sim cannot fill.** Names ride the join handshake and never enter a frame, so `MatchResultReader.TryRead` takes an optional `nameLookup` and leaves the field null without one. The server resolves it against the live room roster (`SimCallbacks.ResolveRoster` walks `RoomManager` for the room whose `Callbacks` is itself); the client passes nothing.
- **The map names itself.** `MapLayoutAsset.MapName` is filled by both exporters from the scene's *filename*, never the root node name (load-bearing in `NodePath`s) or an authored `[Export]` (the footgun `ResolveTeam` exists to avoid — a duplicated map scene would silently keep the old name). It is an id, not a display label; a pretty name belongs in a client catalog keyed off it, the way `FactionCatalog` carries what `FactionAsset` doesn't. Adding a field to this asset invalidates `MapLayout.bytes` — the generated deserializer reads positionally with no short-buffer guard, so re-run `just export-scene-data` in the same change.
- The written file wraps the result in a `MatchRecord` whose `Session` block holds what only the server knows — wall-clock `SavedAtUtc`, `RandomSeed`, `MaxPlayers`/`MinPlayers`. It lands in `Results/` next to the server executable, one file per match, named by timestamp and end tick.
- The sim keeps ticking through Klotho's post-match grace window (`EndGraceMs`), so the client gates input on `MatchOutcome.Ended` in `InputCapture` — otherwise orders issued after the winner is decided still execute.

# Navigation & Temporal Spreading

- `NavigationAgentSystem` handles all unit movement: hero A* pathfinding, minion flow-field steering, ORCA avoidance, and movement integration.
- **Temporal spreading** distributes expensive phases across frames via `NavigationTuningAsset` (row `AssetId: 112` in `client/Sim/Data/Assets/rules.json`):
  - `HeroSteeringSpread` — A* steering update interval (default 1 = every tick)
  - `MinionSteeringSpread` — flow field steering interval (default 1)
  - `AvoidanceSpread` — ORCA collision avoidance interval (default 1)
  - Set to N to update 1/N of agents per tick. Phases are offset (0, 1, 2) so they don't spike the same frame.
- The same asset holds the steering/settle tuning (arrival radii, brake distance, blocked/stuck settle thresholds, ORCA neighbour radius and time horizon, nav-agent acceleration factor). Distances are authored linearly; the system squares them per tick.
- `NavigationRuntime` is built before any frame exists, so it leaves ORCA at Klotho defaults; `NavigationAgentSystem` pushes `AvoidanceTimeHorizon` onto it each tick.
- **A prop must never bake a walkable surface on its own roof.** Recast marks every flat, sky-facing surface walkable and cannot tell a box top from the floor, while `FPNavMeshQuery.FindTriangle` is **XZ-only** — so a roof triangle makes the ground under it read as walkable, and a click there resolves onto an island no unit can path to (the order is accepted and the unit never moves). `agent_max_climb` does not help: it stops the roof *linking* to the floor, which is exactly what makes it an unreachable island. The fix is a carving [`NavigationObstacle3D`](../client/Scenes/Objects/Fountain.tscn) inside the prop scene — it removes navmesh across its whole vertical band, so it takes the roof out along with the footprint and cannot produce one by construction. `filter_baking_aabb` is **not** an alternative: it culls whole source objects rather than clipping them in Y, so anything taller than the box stops carving its hole entirely.
- [`NavTargets.ResolveMoveTarget`](Navigation/NavTargets.cs) is the **one** place a clicked point becomes a destination, and the client calls it too — `InputCapture` resolves the right-click through it, sends the result, and draws the move marker at the same point `CommandSystem` will re-resolve the command to. That only holds because the mover-independent overload is **idempotent**: re-running it on its own output returns that output, so client and sim never disagree. Both snap paths land exactly *on* the boundary, so it then backs the point `MovementRulesAsset.MoveTargetEdgeClearance` off the nearest unwalkable edge — a destination on a wall is one avoidance and the agent radius keep pushing it off, so it grinds along the edge instead of arriving. Structure approach targets keep the plain `SnapToWalkable`: the attacker's range check clears the move target on the near rim, so clearance buys nothing there.
- **Flow fields are runtime state, not frame state.** [`FlowFieldCache`](Navigation/FlowFieldCache.cs) hangs off `NavigationRuntime` and survives rollback, which is safe only because a field is a pure function of the navmesh and the goal triangle — nothing about *when* one is built or evicted can reach the simulation. That is also what lets [`FlowFieldBuilder`](Navigation/FlowFieldBuilder.cs) reuse its working buffers between builds, the cache evict LRU past 64 entries, and `TriangleFlowField` fill exit directions in on demand. Anything goal-dependent that isn't a pure function of those two inputs does not belong in here.
- `FlowFieldBuilder` precomputes the per-edge traversal costs once, because the fixed-point sqrt behind `magnitude` was most of a build. Its Dijkstra pops by (cost, triangle index), so the parent chosen among equal-cost routes is fixed by the navmesh — an unordered tie-break would still be deterministic across peers, but it would silently rewrite minion routes on any change to the queue.
- Movement integration and transform sync run every tick regardless of spread, keeping positions smooth.
- spread=N multiplies each agent's steering refresh interval by N ticks (see `server/simulationconfig.json` for the tick rate). Small values stay within the genre's acceptable latency for AI-controlled units.

# Filter Iteration

**Inside a `frame.Filter<...>` loop, never add or remove any of that filter's own component types — on any entity, including the one the filter just handed you. Collect the entities into a system-owned `List<EntityRef>` and apply the change after the loop.** Components outside the filter's type list are free to add and remove inline, and so is `DestroyEntity` on an entity no live filter is walking.

A `Filter` is a `ref struct` that snapshots `Count` and holds a span over the live dense array of *one* of its storages — the smallest, chosen at construction, so which one is a runtime detail you cannot see at the call site. `ComponentStorageFlat.Remove` compacts by swapping the last dense slot into the removed one, which moves an entity the filter has not reached yet into a slot it has already passed. The visible failure is an entity visited twice in one pass (or, for the single-type `Filter<T1>`, which has no `Has` re-check, a *removed* entity visited and its stale component read). Both are silent and both desync a rollback replay.

Removing the current entity's own component happens to survive this, because the stale dense tail past the new `Count` still resolves through `Has()` — but that is an accident of the layout, not a guarantee, so the rule covers it too. `CommandSystem`, `AttackIntentSystem`, `OasisSpawnSystem`, `DeathSystem`, `ProjectileSystem`, `PickupSystem`, and `TeamPruneSystem` all defer, and nothing in `sim/` may reintroduce the inline form.

# Working Rules

- Prefer compact intent commands with stable `UnitIdComponent.UnitId` references. Do not put transient ECS entity ids in command payloads.
- Movement is planar: `TransformComponent.Position.x/z`.
- NO dynamic physics. Use deterministic transform integration, radii, proximity queries, grids, and stable iteration order.
- When changing gameplay rules, inspect `sim/` first instead of duplicating logic in `client/` or `server/`.
- Klotho asset id ranges (both the AssetId and wire TypeId planes) are tracked in `sim/Assets/AssetIds.cs`; allocate from the "next free" markers there.
- Randomness is derived, never carried. Every `DeterministicRandom` stream comes from `SimRandom.WorldSeed` plus a feature key allocated in [`SimRandom`](SimRandom.cs) and an index built from frame data (`OasisSpawnSystem` uses oasis id + tick, `CriticalStrikes` attacker unit id + tick), so no RNG state crosses a tick and a rollback replay draws the same numbers. A stream that remembers where it left off would leak the discarded prediction branch into the replay.
- Systems hold no tuning constants. Gameplay numbers live in `client/Sim/Data/Assets/` — one `*.json` array per topic, per-hero files under `heroes/` — and are read through `frame.AssetRegistry.Get<T>()`. `AssetGen` merges every `*.json` under that directory recursively, so a new file needs no index entry; after editing run `dotnet run --project tools/AssetGen` to rebuild `Assets.bytes`. It fails on a duplicate `AssetId` or a row without one.

# Ownership

Two id spaces, and they do not mix:

- **`TeamComponent.TeamId`** is the sim's answer to every "may this actor do this" question. Control (`UnitLookup.TryGetPlayerControllableUnitById`), hostility (`CombatTargeting.IsHostileAndAlive`), attack-order targeting, shop proximity, and kill credit all resolve through team. A player reaches their units via `Hero.PlayerId` → `TryGetPlayerTeamId` → team, so player-scoped rules never need a second owner field.
- **`OwnerComponent.OwnerId` is a player id, and belongs only on the hero.** It is a Klotho built-in that the *view* layer reads as a player id: `EntityViewFactory.TryGetBindBehaviour`/`GetViewFlags` compare it against `Engine.LocalPlayerId` to choose predicted vs. verified render, and `EntityViewUpdaterNode` keys `PlayerViewRegistry` off it. Putting a team id there makes team 1's units render off the predicted frame for player 1 while team 2's interpolate — the ids happen to both number from 1, so it looks correct and silently isn't. Minions, crystals, and turrets carry no `OwnerComponent`; `OwnersMatch` short-circuits to true for entities without one, so their views need no `OwnerMatches` override.

# Command Handling

- [`CommandSystem.OnCommand`](Systems/CommandSystem.cs) is a switch and nothing more: it runs [`CommandValidation.Accept`](Commands/CommandValidation.cs), then delegates. A command's rules live in a static `*Actions` class — [`SkillActions`](Heroes/SkillActions.cs) (upgrade, cast), [`ShopActions`](ShopActions.cs) (purchase), [`FactionActions`](FactionActions.cs) (faction pick) — so each rule set can be exercised without a wire round-trip and the dispatcher never grows a body. Each exposes a `Try*` returning `bool` and funnels every bailout through one private `Reject` logger, so a rejection is always one line with a `reason=`. Move and attack orders are the two still handled inline, because they own the selection/formation plumbing.
- **Where `CommandSystem` sits in `RegisterSystems` has nothing to do with command intake.** `EcsSimulation.Tick` drains every `OnCommand` before it calls `RunUpdateSystems`, so orders have already applied by the time the first Update system runs, whatever the registration order. That slot governs only `CommandSystem.Update` — the transform integrator for whatever `NavigationAgentSystem` will not carry: every unit when `navigation` is null, otherwise just move targets held by non-nav agents. It is registered beside the nav branch so both movement paths land at the same point in the frame.
- [`UnitIntent`](UnitIntent.cs) is the **only writer** of `UnitMoveTarget` and `AttackTargetUnitId`, so an order means the same thing wherever it came from. `SetMoveTarget` flattens `y` itself — a pursuit order reads its target's transform, and a structure's comes off a map marker that carries a height. `SetAttackTarget` writes the order alone; resolving it into `Combat.TargetUnitId` is `AttackIntentSystem`'s job. `ClearAttackIntent` drops both together.
- A `UnitLookup.Index` field on a system is **storage, not state**: `Rebuild` clears and refills one dictionary so repeat orders cost no allocation, but its contents must never outlive the command that asked for them — an index kept across ticks survives a rollback and resolves ids against a frame that no longer exists. Rebuild at the entry point and pass the index as a parameter, rather than leaving it on the field for a later method to find.
- **An `*Actions` rule the client needs to ask about gets a read-only `Can*` predicate beside its `Try*`, and both run one evaluation** (see the shared-simulation rule in the root [`AGENTS.md`](../AGENTS.md)). [`SkillActions`](Heroes/SkillActions.cs) is the worked example: `EvaluateCast`/`EvaluateUpgrade` return a `SkillBlock` code, `TryCast`/`TryUpgrade` turn a block into the `reason=` log, and `CanCast`/`CanUpgrade` just compare against `None`. Render the reason text only on the reject path — the client polls the predicate every HUD sync and must not allocate to be told "yes".
- `ShopActions.IsHeroNearTeamShop` is the single range rule for shops, and the client's `ActionBarController` calls it rather than measuring against the selected `ShopEntity` node. The node's transform comes from `World.tscn` and the sim's from the `MapLayoutAsset` Shop marker (exported from the `SimMarker` child of the same prefab); wherever those two drift, measuring against the node would enable a button the sim then rejects with nothing but a log line.
- A client-side gate keeps a known-bad command off the wire; it does not make the rejection cheap when one still lands. Every sim log line is emitted once per *execution* of its tick, and a server-driven client replays its whole predicted window on each verified batch — so a raw `frame.Logger` call in a system reappears a dozen times per event. Gameplay logging goes through [`SimLog`](SimLog.cs), which the client binds to the engine stage so replayed ticks stay quiet.

# Command Validation

Command payloads come off the wire from untrusted peers, and nothing between the socket and the simulation catches an exception. The path runs through Klotho's networking layer in `vendor/Klotho` (not the project's own `server/`): LiteNetLib's `ProcessEvent`, `ServerNetworkService.HandleClientInputMessage`, and `ServerLoop.ExecuteCycle` all let one propagate, and `ServerLoop.Run` wraps the loop in `try`/`finally` with no `catch`. A command that throws or corrupts state while deserializing takes the server process down with every room on it, so validation is not optional for a new command type.

Every command passes through two layers before a handler runs:

1. **Structural**, inside the command's own `DeserializeData`. A variable-length field must never size a buffer or advance the reader from an unchecked wire count. See [`UnitIdList.Deserialize`](Commands/UnitIdList.cs) for the pattern: reject a negative or over-cap count, refuse a count whose bytes are not present, skip a payload that is present but over-cap (catchup and spectator batches read several commands from one reader, so an unread payload misaligns the rest of the batch), and expose the verdict as an `IsValid` flag. Commands are pooled and only `PlayerId`/`Tick` are reset on rent, so every field the deserializer owns must be reassigned on every pass.
2. **Domain**, in [`CommandValidation.Accept`](Commands/CommandValidation.cs), called once from `CommandSystem.OnCommand`. Checks that each field names something that can exist — a coordinate inside the world envelope, an asset id the registry knows. Handlers then spend their own checks on game state (ownership, gold, range), which is where those belong.

Both layers run inside the simulation so client prediction and the authoritative server reach the same verdict for the same frame. Validating on the server ingest path instead would accept a command locally that the server discarded, and the client would mispredict every time.

Wire limits live in [`CommandLimits`](Commands/CommandLimits.cs), not `Assets.json`: they must be identical on both sides and stable across recorded replays. `MaxSelectedUnits` is derived from the unreliable-datagram budget, since LiteNetLib throws rather than fragment an unreliable packet — an oversized selection would crash the sending client too.

# Test Cheats

`--godmode` on the client command line makes that player's hero take no damage. The flag is parsed by [`CheatOptions`](../client/Scripts/View/CheatOptions.cs), sent as `SetCheatCommand`, and stored per player in the `CheatState` singleton, which [`Cheats`](Cheats.cs) reads and `DamageApplication` gates on. Nothing authorizes the command beyond scoping it to the issuing player, so it is a development aid rather than a mode a shipped server should accept.

Adding another cheat: a value in [`CheatFlags`](Enums.cs), the same bit in `Cheats.All` so validation accepts it, the arg in `CheatOptions`, and the read wherever the rule lives. The command and the storage need no change.

`godmode` is a justfile variable, so the assignment goes **before** the recipe name — `just godmode=true quickplay 1000 202 201` — and `play`, `quickplay`, and `smoke` all pass it to both clients. After the recipe name it would be read as a positional argument instead.
